# 规格优先开发哲学

> TestSpec 框架的核心理念：为什么要先写规格，再写测试。

---

## 一、从问题出发：测试自动化的"感觉编码"困境

### 什么是感觉编码（Vibe Coding）

"感觉编码"指的是：开发者凭借对系统的直觉和经验，跳过需求分析直接动手写代码的行为模式。在普通业务代码中，这种方式有时能快速出结果；但在测试自动化领域，它会带来系统性的隐患。

### 测试自动化中感觉编码的典型症状

**症状 1：覆盖遗漏**
工程师根据记忆写测试，往往只覆盖了"开心路径"（happy path），忽略了边界条件、异常路径、权限组合。问题不是工程师能力不足，而是缺乏系统性的用例设计过程。

**症状 2：无法追溯**
三个月后，没有人知道某个测试函数对应的是哪条需求。需求变更时，找不到应该同步修改的测试。代码的"为什么"彻底消失在历史记录中。

**症状 3：AI 助手的幻觉放大效应**
当工程师用自然语言提示 AI"帮我写一个登录测试"时，AI 会基于统计模式生成看起来合理的代码，但这些代码：
- 未必覆盖了业务真正的异常场景
- 断言可能是空洞的（只判断 status_code = 200）
- 数据库校验几乎肯定缺失
- 清理策略可能被遗漏

AI 的高效输出掩盖了设计的缺失，制造出"已经覆盖"的假象，这比手写代码遗漏更危险——因为它更难被发现。

**症状 4：技术债堆积**
缺乏结构的测试代码随着功能迭代快速腐化。新功能上线，没有人能确定应该修改哪些测试、新增哪些用例，最终选择绕开，测试套件逐渐失去意义。

## 二、规格优先：解决思路

### 核心主张

> 测试用例的价值不在于代码，而在于对系统行为的规格化描述。代码只是规格的一种执行形式。

规格优先开发（Spec-First Development）要求：**在写任何一行测试代码之前，先用自然语言（结构化文档）描述清楚"要验证什么"**。

这不是新概念。行为驱动开发（BDD）、测试驱动开发（TDD）都包含类似思想。TestSpec 的贡献在于：将这一思想与 AI 辅助工具链结合，形成可操作的工程规范。

### 规格的三个作用

**作用 1：AI 对齐锚点**
当 AI 助手拿到结构化规格文档（用例清单、覆盖维度表）而非模糊提示时，生成代码的质量会大幅提升。规格文档像合同一样约束 AI 的输出范围，而不是任由它发挥想象。

**作用 2：人机共同语言**
规格文档是团队成员（产品、开发、测试、AI）之间的共同语言。它不依赖任何技术实现，可以被所有角色理解和审查。

**作用 3：变更响应基础**
需求变更时，先更新规格文档，再由规格文档驱动测试代码的修改。这样可以精确定位变更影响范围，避免遗漏或过度修改。

## 三、8 步工作流：规格到代码的完整路径

TestSpec 框架将测试开发过程分解为 8 个步骤，每步都有明确的输入、输出和验收标准。

```
规格文档
    │
    ▼ 步骤 0：规格对齐
业务需求理解 + 追溯表建立
    │
    ▼ 步骤 1：用例设计
结构化用例清单（场景 × 维度矩阵）
    │
    ▼ 步骤 2：测试数据设计
数据驱动用例的 YAML/参数化设计
    │
    ▼ 步骤 3：代码编写
pytest 代码框架（fixture + helper + 测试函数）
    │
    ▼ 步骤 4：断言设计
断言策略（字段选择 + 类型 + 边界）
    │
    ▼ 步骤 5：数据库校验
DB 校验查询（写/改/删接口必须）
    │
    ▼ 步骤 6：报告装饰
Allure 注解（title/step/attach/severity）
    │
    ▼ 步骤 7：合规自检
自动扫描：写操作是否缺 DB 校验
    │
    ▼
可交付的测试套件
```

### 为什么是 8 步而非 1 步

这 8 步不是任意拆分，每步都解决特定问题：

- **步骤 0-1（规格层）**：防止遗漏和幻觉
- **步骤 2（数据层）**：确保测试独立性和可重复性
- **步骤 3（代码层）**：结构化生成，而非自由发挥
- **步骤 4-5（验证层）**：确保断言有实质意义
- **步骤 6（可观测层）**：为报告和追踪提供基础
- **步骤 7（门禁层）**：防止遗漏落库到生产

跳过任何一步都会在对应层引入风险，而这些风险通常在很晚才被发现。

## 四、规格作为"单一真相来源"

### 传统模式的问题

```
需求文档（PRD） ←--- 人工同步 ---→ 测试用例（Excel/Word）
                                         │
                                    人工转化
                                         │
                                   测试代码（Python）
```

三份产物各自独立，同步依赖人工，一旦出现分歧，无法判断哪份是权威。

### 规格优先模式

```
规格文档（specs/）  ←--- 是唯一真相 ---→ 永远不过时
        │
        │ 驱动（AI + 人工审查）
        ▼
  用例清单（结构化）
        │
        │ 驱动（AI 代码生成）
        ▼
  测试代码（Python）
        │
        │ 驱动（合规自检）
        ▼
  覆盖报告（可追溯）
```

`specs/` 目录下的文档是整条链路的起点。代码的存在是为了执行规格，而不是规格的原始来源。

### 追溯链设计

每个测试函数通过 `@allure.title` 和函数命名，可以追溯到：
1. 具体的规格文档（`specs/<业务线>/xxx.md`）
2. 用例清单中的具体条目
3. 覆盖的需求维度（正常/异常/边界/权限）

这使得以下操作成为可能：
- 需求变更时，精确找到受影响的测试
- 代码审查时，验证覆盖完整性
- 问题排查时，快速定位对应的业务规格

## 五、与 OpenSpec SDD 的比较

### OpenSpec 的规格驱动开发（SDD）

OpenSpec 的 SDD（Spec-Driven Development）方法论强调：API 规格（OpenAPI/Swagger）是开发的单一真相来源，客户端、服务端、文档、测试都从同一份规格生成。

### 相似之处

| 维度 | TestSpec | OpenSpec SDD |
|---|---|---|
| 核心理念 | 规格先行，代码后行 | 规格先行，代码后行 |
| 真相来源 | `specs/` 目录文档 | OpenAPI 规格文件 |
| AI 角色 | 规格驱动代码生成 | 规格驱动代码生成 |
| 追溯性 | 代码 ↔ 规格双向追溯 | 代码 ↔ 规格双向追溯 |

### 本质差异

| 维度 | TestSpec | OpenSpec SDD |
|---|---|---|
| 规格格式 | 自然语言文档（Markdown） | 机器可读格式（YAML/JSON） |
| 应用场景 | 测试设计 | 接口设计 |
| 规格作者 | 测试工程师 / 产品 | 接口设计者 |
| 代码产物 | 测试代码（pytest） | 客户端/服务端代码 |

两者的哲学相同，但 TestSpec 更侧重"验证"语义，而 OpenSpec SDD 更侧重"定义"语义。两者可以在同一项目中共存：OpenAPI 规格定义接口契约，TestSpec 规格定义测试场景。

## 六、什么时候适合用 TestSpec，什么时候可能过重

### 适合使用 TestSpec 的场景

- **长期维护的测试套件**：团队超过 2 人、预期运行 6 个月以上
- **业务逻辑复杂**：多条业务线、多种异常场景、权限矩阵复杂
- **AI 辅助开发**：使用 AI 工具生成测试代码，需要规格作为约束
- **合规要求**：需要测试覆盖率报告或需求追溯矩阵
- **数据库操作**：涉及写操作的接口测试，DB 校验是必须的

### 可能过重的场景

- **一次性脚本**：临时验证某个接口是否可达，写完即弃
- **极小型项目**：1-2 人、5 个以内的测试文件、简单 CRUD
- **纯单元测试**：函数级别的纯逻辑验证，无外部依赖
- **原型验证阶段**：需求本身还未稳定，规格会频繁重写

### 轻量化建议

如果认为完整 8 步过重，可以选择性采用：
- **最小化必须步骤**：步骤 1（用例设计）+ 步骤 3（写代码）+ 步骤 7（合规自检）
- **跳过可选步骤**：步骤 2（数据）、步骤 4（断言设计）在简单场景可以内联
- **简化报告**：步骤 6（Allure 装饰）对于 CI 快速验证场景可以简化

但有一条原则无论如何不应跳过：**写操作接口必须有数据库校验**。这是防止测试产生脏数据的最后防线。

## 七、总结

规格优先不是一种负担，而是一种投资。

短期来看，它增加了前期的文档成本；长期来看，它减少了调试时间、降低了遗漏风险、提升了团队协作效率，也让 AI 工具真正成为"规格到代码"的可靠翻译器，而不是貌似聪明的代码生成机器。

TestSpec 框架的存在，就是为了把这种投资的成本降到最低，把回报最大化。
