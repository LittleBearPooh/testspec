# 8 步工作流详解

> TestSpec 框架完整工作流的操作手册：每步的输入/输出/技能命令/常见陷阱。

---

## 总览

| 步骤 | 名称 | 命令 | 必须/推荐 | 核心产物 |
|---|---|---|---|---|
| 0 | 规格对齐 | `/case-design`（内含） | **必须** | 需求理解确认 + 追溯表 |
| 1 | 用例设计 | `/case-design` | **必须** | 结构化用例清单 |
| 2 | 测试数据设计 | `/test-data` | 推荐 | YAML 参数化数据文件 |
| 3 | 代码编写 | `/write-tests` | **必须** | pytest 测试文件 |
| 4 | 断言设计 | `/assertion-design` | 推荐 | 断言策略说明 + 代码补充 |
| 5 | 数据库校验 | `/data-verify` | **必须**（写/改/删） | DB 查询语句 + 校验代码 |
| 6 | 报告装饰 | `/report-decorate` | **必须** | Allure 注解补全 |
| 7 | 合规自检 | `/compliance-check` | **必须** | 缺失清单或 OK |

---

## 步骤 0：规格对齐

### 目标

在写任何测试之前，先确认 AI 和工程师对"要验证什么"有一致的理解。

### 输入

- `specs/<业务线>/` 目录下的需求文档、接口文档、业务规则说明
- 需求变更记录（如果是对已有功能的修改）

### 执行方式

步骤 0 内嵌在 `/case-design` 命令中。调用时，AI 会自动：
1. 读取 `specs/<业务线>/` 下的相关文档
2. 提炼关键业务规则和约束条件
3. 生成初步的需求追溯表（requirement → test scenario 的映射）
4. 向工程师确认理解是否正确

### 输出

```markdown
## 需求追溯表

| 需求 ID | 需求描述 | 测试场景 | 覆盖维度 |
|---|---|---|---|
| REQ-001 | 用户登录成功 | test_login_success | 正常路径 |
| REQ-002 | 密码错误时返回 401 | test_login_wrong_password | 异常路径 |
| REQ-002 | 账号锁定后无法登录 | test_login_locked_account | 边界条件 |
```

### 常见陷阱

- **陷阱 1：跳过此步直接写代码**。后果是 AI 会基于自己的"直觉"生成用例，可能遗漏项目特有的业务规则（如特定状态机的流转限制）。
- **陷阱 2：specs 目录为空**。此时应先补充基础规格文档，哪怕是一份 2-3 页的需求概述也比没有强。
- **陷阱 3：需求文档过期**。使用前确认文档版本与当前系统行为一致，否则追溯表会产生误导。

### 适应不同测试类型

| 测试类型 | 规格来源 | 重点关注 |
|---|---|---|
| API 测试 | 接口文档（OpenAPI/手写 Markdown） | 请求参数组合、错误码定义 |
| 单元测试 | 函数/类的设计文档或注释 | 输入边界、异常处理 |
| 集成测试 | 系统交互图、数据流图 | 跨系统数据一致性 |
| E2E 测试 | 业务流程图、用户故事 | 完整业务流转、状态机 |

## 步骤 1：用例设计

### 目标

将规格文档转化为结构化的用例清单，作为后续代码生成的"合同"。

### 输入

- 步骤 0 产出的追溯表
- `specs/<业务线>/` 文档
- 工程师对覆盖优先级的说明（P0/P1/P2）

### 技能命令

```
/case-design
参数建议：说明业务线名称、接口名称、需要覆盖的维度（正常/异常/边界/权限）
```

### 输出格式

```markdown
## 用例清单：OrderCreate 接口

### 正常路径（P0）
- [ ] 标准下单：必填参数齐全，返回 201 + 订单号
- [ ] 含可选参数下单：含备注字段，字段正确落库

### 异常路径（P1）
- [ ] 缺少必填参数 itemId：返回 400
- [ ] 无效的 productId：返回 404
- [ ] 库存不足：返回 422 + 具体错误信息

### 边界条件（P1）
- [ ] 开始日期等于今天：正常处理
- [ ] 开始日期早于今天：返回 400
- [ ] 备注字段超过最大长度：返回 400 或截断（确认业务规则）

### 权限场景（P2）
- [ ] 未登录请求：返回 401
- [ ] 无下单权限的账号：返回 403
```

### 为什么用例设计必须先于代码

1. **覆盖可审查**：用例清单可以由产品、测试负责人、开发三方共同确认，而代码只有工程师能审。
2. **优先级明确**：P0 用例必须写，P2 可以延后；这个决策在设计阶段做，而不是写了一半再删。
3. **AI 边界约束**：用例清单告诉 AI"写哪些"，防止 AI 自行增删场景。

### 常见陷阱

- **陷阱 1：用例描述太笼统**，如"测试下单功能"。正确做法：每条用例描述一个具体的输入条件 + 预期结果。
- **陷阱 2：只写正常路径**。异常路径往往覆盖了 80% 的 bug，必须在设计阶段明确。
- **陷阱 3：没有确认业务规则的边界**（如上例中备注字段超长是截断还是报错）。在写代码前通过文档或询问确认，比写完代码再改便宜。

## 步骤 2：测试数据设计

### 目标

为参数化用例设计 YAML/JSON 数据文件，确保：测试数据唯一、结构清晰、便于维护。

### 何时需要此步骤

- 同一个测试逻辑需要用多组参数覆盖（数据驱动测试）
- 测试数据需要版本管理（如预定义的测试账号、测试商品 ID）
- 数据量较大，内联在代码中会影响可读性

### 技能命令

```
/test-data
参数建议：说明需要哪些数据字段、覆盖哪些维度、是否需要动态生成
```

### 输出示例

```yaml
# data/yaml/order_create_cases.yaml
- id: normal_full_params
  desc: "标准下单：所有必填 + 可选参数"
  product_id: 1001
  item_id: 2001
  start_date: "2026-08-01"
  end_date: "2026-08-03"
  remark: "测试备注_{{TEST_RUN_ID}}"
  expected_status: 201

- id: missing_item_id
  desc: "缺少必填参数 itemId"
  product_id: 1001
  start_date: "2026-08-01"
  end_date: "2026-08-03"
  expected_status: 400
  expected_error: "itemId is required"
```

### 数据唯一性原则

测试数据必须在并发执行时不互相冲突。常用策略：
- 使用 `faker` 或 `uuid` 生成唯一字符串作为标识
- 在数据字段中嵌入 `pytest` 的 `worker_id`（xdist 并行时）
- 固定 ID 只用于只读操作（查询），写操作必须动态生成数据

### 常见陷阱

- **陷阱 1：使用生产数据 ID**。生产数据可能被删除或修改，导致测试不稳定。
- **陷阱 2：测试间共享可变状态**（如同一个订单 ID 被多个测试修改）。
- **陷阱 3：忘记清理**。每个创建型用例必须有对应的清理逻辑（teardown 或 autouse fixture）。

## 步骤 3：代码编写

### 目标

基于用例清单和数据文件，生成结构化的 pytest 测试代码。

### 技能命令

```
/write-tests
参数建议：
- 说明测试文件放置路径
- 说明 token 获取方式（如"token 从 xxx/client/token_store.py 获取"）
- 说明是否需要 DB 校验（是/否，对应后续步骤 5）
- 说明是否需要清理策略（是，创建型用例必须有）
```

### 代码结构规范

```python
# testcase/<业务线>/test_order_create_e2e.py

import allure
import pytest
from utils.logger import get_logger

logger = get_logger(__name__)


@allure.epic("订单管理")
@allure.feature("下单流程")
class TestOrderCreate:

    @allure.title("标准下单：必填参数齐全，返回订单号")
    @allure.severity(allure.severity_level.CRITICAL)
    @pytest.mark.e2e
    def test_CreateOrder_ReturnsOrderNumber(self, api_client, cleanup_orders):
        """P0 - 正常路径：标准下单"""
        with allure.step("准备下单参数"):
            params = {...}
            allure.attach(str(params), name="请求参数", attachment_type=allure.attachment_type.TEXT)

        with allure.step("调用下单接口"):
            resp = api_client.create_order(**params)
            allure.attach(str(resp), name="响应结果", attachment_type=allure.attachment_type.TEXT)

        with allure.step("断言响应"):
            assert resp["order_number"] is not None
            assert resp["status"] == "PENDING"
            # 注册到清理列表
            cleanup_orders.append(resp["order_number"])

        with allure.step("数据库校验"):
            # 步骤 5 补全
            pass
```

### 关键约定

1. **每个测试函数必须有 `@allure.title`**。
2. **每个 `allure.step` 块内必须有 `allure.attach`**，输出该步骤的关键数据。
3. **清理策略必须在创建成功后立即注册**，不能等到断言通过后。
4. **不得在函数体内 import**，所有 import 放在文件顶部。
5. **不在函数体内硬编码凭据**，通过 fixture 或 `variables.yaml` 获取。

### 常见陷阱

- **陷阱 1：一个测试函数覆盖多个场景**。每个函数只覆盖一个场景，函数名清晰表达输入条件和预期结果。
- **陷阱 2：裸 `time.sleep` 等待异步结果**。正确方式：带超时的轮询循环。
- **陷阱 3：忘记 `allure.attach`**。步骤中没有 attach，报告就像黑盒，排查问题时效率极低。

### 适应不同测试类型

| 测试类型 | 典型 fixture | 清理策略 |
|---|---|---|
| API 测试 | `http_client`、`api_client` | `autouse` fixture + 清理注册表 |
| 单元测试 | 无或 mock patch | 通常不需要（无副作用） |
| 集成测试 | 多个服务 client | 事务回滚或专用清理接口 |
| E2E 测试 | 完整业务流 client | 业务取消/关闭接口 |

## 步骤 4：断言设计

### 目标

确保断言有实质意义，不只是检查 HTTP 状态码。

### 何时使用此步骤

- 接口返回字段多（20+ 个字段），不知道该断言哪些
- 断言策略不明确（是断言精确值，还是断言类型，还是断言存在性）
- 有嵌套 JSON 结构需要部分断言

### 技能命令

```
/assertion-design
参数建议：粘贴接口响应的 JSON 结构，说明业务语义
```

### 断言分层策略

| 断言层次 | 内容 | 何时使用 |
|---|---|---|
| 状态断言 | HTTP status_code | 每个测试必须有 |
| 结构断言 | 关键字段存在性（is not None） | 所有非空字段 |
| 语义断言 | 字段值等于业务预期 | 核心业务字段 |
| 稳定性断言 | 未修改字段保持不变 | 更新操作 |
| DB 一致性断言 | 响应值与数据库值一致 | 所有写操作 |

### 常见陷阱

- **陷阱 1：只断言 `status_code == 200`**。这是最常见的无效断言，接口逻辑错误但状态码正确时无法发现。
- **陷阱 2：断言所有字段的精确值**。对动态字段（如时间戳、自增 ID）断言精确值会导致测试脆弱。
- **陷阱 3：用 `assert resp != {}`** 之类的空检查替代实质断言。

## 步骤 5：数据库校验

### 目标

验证写操作确实影响了数据库，且数据与业务规则一致。

### 覆盖范围

| 操作类型 | 必须校验 | 可选校验 |
|---|---|---|
| 新增 | 记录存在、关键字段值正确 | 关联表一致性、触发器效果 |
| 更新 | 变更字段新值正确、未变更字段保持原值 | 更新时间戳、操作日志 |
| 删除 | 软删除：deleted_at 非空或 status 变更；物理删除：记录不存在 | 关联数据级联 |
| 失败场景 | 数据库无脏数据（记录不存在或未变更） | — |

### 技能命令

```
/data-verify
参数建议：说明表名、关键字段、预期值、是否是软删除
```

### 代码示例

```python
with allure.step("数据库校验：验证订单已落库"):
    from utils.db_client import get_db
    db = get_db("main_db")

    # 带超时轮询（异步落库场景）
    import time
    deadline = time.monotonic() + 10  # 10 秒超时
    db_order = None
    while time.monotonic() <= deadline:
        db_order = db.query_one(
            "SELECT * FROM Orders WHERE OrderNumber = %s",
            (order_number,)
        )
        if db_order:
            break
        time.sleep(0.5)

    assert db_order is not None, f"订单 {order_number} 未在数据库中找到"
    assert db_order["Status"] == "PENDING"
    assert db_order["OrderId"] == expected_order_id
    allure.attach(str(db_order), name="DB 记录", attachment_type=allure.attachment_type.TEXT)
```

### SQL 安全规则

- 永远使用参数化查询（`%s` 占位符 + 参数元组）
- 禁止字符串格式化拼接 SQL（f-string / % 格式化）
- 查询结果为空时断言失败，而非静默跳过

### 常见陷阱

- **陷阱 1：跳过 DB 校验**。接口返回 200 但数据未落库是真实存在的 bug，只有 DB 校验能发现。
- **陷阱 2：直接 sleep 等待异步落库**。正确做法：带超时的轮询循环，最大等待时间根据业务配置。
- **陷阱 3：校验失败场景时忘记断言"无脏数据"**。失败路径产生的脏数据可能影响后续测试或生产数据。

## 步骤 6：报告装饰

### 目标

补全 Allure 注解，让测试报告对非技术人员也可读，并支持用例追踪。

### 技能命令

```
/report-decorate
参数建议：说明测试文件路径，让 AI 扫描并补全缺失的注解
```

### 必须有的注解

| 注解 | 位置 | 说明 |
|---|---|---|
| `@allure.title` | 每个测试函数 | 用于统计、报告标题、追踪 |
| `@allure.severity` | 每个测试函数 | BLOCKER/CRITICAL/NORMAL/MINOR/TRIVIAL |
| `@allure.epic` | 类或模块级 | 对应业务模块 |
| `@allure.feature` | 类或模块级 | 对应功能特性 |
| `with allure.step(...)` | 测试函数内 | 每个主要操作拆分为步骤 |
| `allure.attach(...)` | 每个 step 内 | 输出关键数据 |

### severity 选择标准

| 级别 | 适用场景 |
|---|---|
| BLOCKER | 核心功能不可用（如下单、支付） |
| CRITICAL | 核心功能有严重缺陷（如数据错误） |
| NORMAL | 普通功能测试 |
| MINOR | 边界条件、格式校验 |
| TRIVIAL | 可选功能、UI 提示 |

### 常见陷阱

- **陷阱 1：`allure.step` 有步骤描述但 `allure.attach` 内容为空**。报告中看到步骤但不知道数据是什么，排查效率极低。
- **陷阱 2：`@allure.title` 描述与函数名重复**。title 应该是对外展示的业务语言，函数名是对内的技术标识，两者可以不同。
- **陷阱 3：所有测试都标 CRITICAL**。severity 失去区分度，优先级排查无从下手。

## 步骤 7：合规自检

### 目标

作为收尾门禁，确保所有写操作用例都有 DB 校验，防止遗漏。

### 技能命令

```
/compliance-check
```

等价于运行：
```bash
python scripts/check_compliance.py
```

### 输出示例

```
[WARN] 发现 2 个写操作用例缺少 DB 校验：

文件: testcase/hotel/test_order_create_e2e.py
  - 行 45: test_CreateOrder_WithRemark → 缺少 db_client 调用

文件: testcase/flight/test_flight_book_e2e.py
  - 行 123: test_BookFlight_Success → 缺少 db_client 调用

请补全上述用例的数据库校验后重新运行自检。
```

### 自动排除规则

以下函数/文件会被自动排除，无需 DB 校验：
- 函数名含 `_contract` 或 `_smoke` 后缀
- 文件名含 `_contract` 的文件
- 只读操作（GET 接口，不修改数据）

### 常见陷阱

- **陷阱 1：自检通过就认为质量达标**。合规自检只检查"有没有 DB 校验"，不检查校验是否正确。校验字段的选择仍需人工审查。
- **陷阱 2：通过添加空的 `db_client` 导入来绕过自检**。这会通过扫描但没有实质校验，属于规避门禁的行为。

## 步骤间依赖链

```
步骤 0（规格对齐）
    └─ 依赖：specs/ 文档存在
    └─ 产出：追溯表
          │
          ▼
步骤 1（用例设计）
    └─ 依赖：追溯表、规格文档
    └─ 产出：用例清单（结构化）
          │
     ┌────┴────┐
     ▼         ▼
步骤 2      步骤 3（代码编写）
（数据）     └─ 依赖：用例清单 + 步骤 2 数据
     │       └─ 产出：pytest 测试文件（含待补全的 DB 校验）
     │              │
     │         ┌────┴────┐
     │         ▼         ▼
     │    步骤 4      步骤 5（DB 校验）
     │   （断言）      └─ 依赖：步骤 3 代码框架
     │         │       └─ 产出：DB 查询 + 断言代码补入步骤 3
     │         │              │
     └─────────┴──────────────┤
                               ▼
                          步骤 6（报告装饰）
                           └─ 依赖：步骤 3+4+5 完整代码
                           └─ 产出：Allure 注解补全
                                    │
                                    ▼
                              步骤 7（合规自检）
                               └─ 依赖：步骤 6 完整代码
                               └─ 产出：通过 OK / 缺失清单
```

**为什么顺序不能随意调整**：
- 步骤 3 依赖步骤 1：没有用例清单就没有"写什么"的边界
- 步骤 5 依赖步骤 3：DB 校验是补充到已有代码框架中的
- 步骤 7 依赖步骤 5：自检的前提是 DB 校验已经写入代码

## 如何为特定项目定制步骤

### 定制维度 1：跳过某些步骤

- 纯查询接口（无写操作）：跳过步骤 5（DB 校验不适用）
- 简单参数化用例（无需独立数据文件）：跳过步骤 2，数据直接内联在 `@pytest.mark.parametrize`
- 不使用 Allure 的项目：跳过步骤 6，用 pytest 原生报告替代

### 定制维度 2：扩展步骤

- 性能要求的用例：在步骤 3 后增加"性能基准设置"步骤（记录响应时间基线）

## 失败排查：步骤外的辅助命令

当用例失败时，使用 `/debug-failure` 命令而非盲目修改代码。

### 调用时机

- 用例在 CI 上失败但本地通过
- 某个断言持续失败，看不出原因
- 数据库校验发现异常数据
- 接口返回预期之外的状态码

### 排查流程

```
/debug-failure
```

AI 会执行以下分析：
1. 检查失败的断言和实际值
2. 检查 Allure attach 中的请求/响应数据
3. 检查数据库中的实际状态
4. 与规格文档对比，判断是测试 bug 还是被测系统 bug
5. 给出修改建议（是修改测试还是提 bug）

### 常见根因分类

| 根因类型 | 典型现象 | 修复位置 |
|---|---|---|
| 测试数据问题 | 并发冲突、ID 不存在 | 测试数据设计（步骤 2） |
| 断言太严格 | 动态字段精确匹配失败 | 断言设计（步骤 4） |
| 异步时序 | DB 数据未就绪就查询 | 替换为带超时轮询 |
| 被测系统 bug | 规格描述的行为与实际不符 | 提 bug，测试逻辑正确 |
| 环境配置问题 | 只在特定环境失败 | variables.yaml / 环境变量 |
